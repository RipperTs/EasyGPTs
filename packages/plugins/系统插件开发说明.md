# 系统插件开发说明（packages/plugins）

本文档面向 EasyGPTs 当前代码实现，目标是让后续 AI/开发者在新增或修改系统插件时，能一次性走通，减少“能看到插件但跑不起来”这类问题。

## 1. 系统插件执行链路（必须理解）

### 1.1 启动加载

1. 服务启动时会初始化系统插件模板与回调：
   - `projects/app/src/service/mongo.ts`
   - 调用：`getSystemPlugins()`、`getSystemPluginCb()`
2. 系统插件来源：
   - 社区版：`packages/plugins/register.ts` 的 `getCommunityPlugins/getCommunityCb`
   - 商业版：走 `projects/app/src/service/core/app/plugin.ts` 的远程接口分支

### 1.2 模板如何出现在前端可选列表

1. API 返回系统插件模板：
   - `projects/app/src/pages/api/core/app/plugin/getSystemPluginTemplates.ts`
2. 前端获取插件模板：
   - `projects/app/src/web/core/app/api/plugin.ts` -> `getSystemPlugTemplates`

### 1.3 插件在工作流中如何执行

系统插件模板本质是一个“插件工作流”，典型结构是：
`pluginInput -> httpRequest468 -> pluginOutput`

执行关键点：

1. `httpRequest468` 节点会读取 `system_httpReqUrl`
2. 若 `system_httpReqUrl` 命中系统插件回调名，则不发真实 HTTP，而是直接执行本地插件函数：
   - `packages/service/core/workflow/dispatch/tools/http468.ts`
   - `const systemPluginCb = await getSystemPluginCb();`
   - `systemPluginCb[httpReqUrl](requestBody)`
3. 插件函数来自：
   - 主线程直接 import：`packages/plugins/src/<name>/index.ts`
   - 或 Worker 线程执行：`packages/plugins/runtime/worker.ts`

### 1.4 Worker 入口来源

1. Worker 名称：`systemPluginRun`
   - `packages/service/worker/utils.ts`
2. Next 构建时注入 worker 入口：
   - `projects/app/next.config.js`
   - `'worker/systemPluginRun': '../../packages/plugins/runtime/worker.ts'`

## 2. 目录与文件职责

### 2.1 `packages/plugins` 内部

- `packages/plugins/register.ts`
  - 系统插件注册中心（最关键）
  - `staticPluginList`：主线程执行
  - `packagePluginList`：Worker 执行（通常依赖第三方 npm 包）
- `packages/plugins/runtime/worker.ts`
  - Worker 模式下动态加载插件模块并执行
- `packages/plugins/src/<plugin>/template.json`
  - 插件模板（前端展示 + 工作流结构）
- `packages/plugins/src/<plugin>/index.ts`
  - 插件具体执行逻辑

### 2.2 服务侧桥接

- `projects/app/src/service/core/app/plugin.ts`
  - 加载模板、加载回调、全局缓存
- `packages/service/core/workflow/dispatch/tools/http468.ts`
  - 运行时根据 `system_httpReqUrl` 决定调用本地插件还是外部 HTTP

## 3. 新增系统插件标准流程（Checklist）

## 3.1 新建插件目录

在 `packages/plugins/src` 下新建：

```bash
packages/plugins/src/<插件名>/
  ├── template.json
  └── index.ts
```

说明：

- 若只是“分组目录”，可只有 `template.json`（如 `duckduckgo`、`Doc2X` 根目录）
- 真正可执行插件必须有 `index.ts`

## 3.2 编写 `index.ts`

约定：

- 默认导出 async 函数
- 入参是模板里 `system_httpJsonBody` 组装后的对象
- 返回值必须是对象（`Record<string, any>`）

最小示例：

```ts
type Props = { text: string };

const main = async ({ text }: Props): Promise<{ result: string }> => {
  return { result: `echo: ${text}` };
};

export default main;
```

## 3.3 编写 `template.json`

关键字段（顶层）：

- `name` / `avatar` / `intro` / `version`
- `isTool: true`
- `templateType`（如 `tools/search/database/communication`）
- `workflow.nodes` + `workflow.edges`

插件工作流建议最小包含：

- `pluginInput`
- `httpRequest468`
- `pluginOutput`

`httpRequest468` 节点关键输入：

- `system_httpMethod`: 通常 `POST`
- `system_httpReqUrl`: **必须等于 register.ts 里的插件注册名**
- `system_httpJsonBody`: 传给 `index.ts` 的请求体模板

## 3.4 注册插件（必须）

编辑：`packages/plugins/register.ts`

1. 将插件名加入 `list`（通过 `staticPluginList` 或 `packagePluginList`）
2. 名称必须与目录相对路径一致，例如：
   - `duckduckgo/search`
   - `drawing/baseChart`

选择规则：

- 无重依赖、轻逻辑：`staticPluginList`
- 依赖三方库、耗时较重：`packagePluginList`

## 3.5 依赖管理

若 `index.ts` 新增第三方依赖，补到：

- `packages/plugins/package.json`

## 4. 字段对齐规则（最容易出错）

## 4.1 `system_httpReqUrl` 与注册名必须一致

例如 `register.ts` 中是 `email`，则 `template.json` 中必须是：

```json
"key": "system_httpReqUrl",
"value": "email"
```

不一致会触发 `http468` 走外部 HTTP 请求分支，导致“插件未命中、本地逻辑没执行”。

## 4.2 返回字段要与输出提取规则对齐

`http468` 会按 `node.outputs` 里的 key 通过 JSONPath 取值（如 `$.result`）。

建议：

- 插件返回结构稳定、扁平
- `pluginOutput` 输入引用 `httpRequest468` 的明确输出字段

## 4.3 特殊返回类型

支持图片类特殊结构（示例见 `drawing/baseChart`）：

```ts
{
  result: {
    type: 'SYSTEM_PLUGIN_BASE64',
    value: 'data:image/...base64,...',
    extension: 'svg'
  }
}
```

## 4.4 工具直出文本

若返回包含 `answerText`（对应 `NodeOutputKeyEnum.answerText`），会触发 SSE `fastAnswer` 直接回显给用户。

## 5. 常见问题与排查

## 5.1 插件在列表里看不到

优先检查：

1. `packages/plugins/register.ts` 是否加入插件名
2. `template.json` 是否存在且 JSON 合法
3. `isActive` 过滤（系统配置层）后是否仍可见

## 5.2 插件能选中但执行报错

优先检查：

1. `system_httpReqUrl` 是否与注册名一致
2. `system_httpJsonBody` 变量占位符是否能正确解析
3. `index.ts` 是否默认导出函数
4. 插件返回是否为对象

## 5.3 Worker 模式插件执行失败

优先检查：

1. 是否放在 `packagePluginList`
2. `packages/plugins/package.json` 依赖是否完整
3. 代码是否使用了 Node 环境可用 API
4. Worker 加载路径是否与目录一致（`../src/${name}/index`）

## 5.4 修改后不生效

建议：

1. 重启开发服务，确保 worker 与动态 import 上下文刷新
2. 确认访问的是当前环境（社区版/商业版分支不同）

## 5.5 单节点调试卡片看不到“输入值”

现象：

- 在画布里“单独运行节点”后，结果卡片只看到输出，看不到输入。

原因：

- 结果卡片的“输入”来自 `nodeResponse.nodeInputs`，不是插件 `index.ts` 的返回字段。
- 系统插件节点调度在 `packages/service/core/workflow/dispatch/plugin/run.ts`；
- 若这里只返回 `pluginOutput`，而未写入 `nodeInputs`，调试卡片就不会显示输入。

修复：

1. 在 `dispatchRunPlugin` 的 `nodeResponse` 中补充 `nodeInputs`（通常可直接使用 `params`）。
2. 对敏感字段做脱敏后再写入 `nodeInputs`，至少包括：`password`、`private_key`、`passphrase`。

示例（伪代码）：

```ts
const maskedInputs = maskSensitive(params);

return {
  [DispatchNodeResponseKeyEnum.nodeResponse]: {
    nodeInputs: maskedInputs,
    pluginOutput
  }
};
```

说明：

- 这是“调试展示链路”逻辑，不应通过修改插件 `index.ts` 返回格式来兜底。

## 6. 推荐开发模板（给 AI 直接用）

可直接把下面内容给 AI：

```text
目标：在 packages/plugins 新增系统插件 <name>。
要求：
1) 新建 packages/plugins/src/<name>/template.json 与 index.ts；
2) 插件工作流使用 pluginInput -> httpRequest468 -> pluginOutput；
3) system_httpReqUrl 必须为 <name>；
4) 在 packages/plugins/register.ts 注册到 <staticPluginList|packagePluginList>；
5) 若有新依赖，更新 packages/plugins/package.json；
6) 返回字段与 template 输出字段严格对齐；
7) 给出手动验证步骤（至少包含：模板可见、执行成功、输出字段正确）。
```
